# PC 版（WHITE ALBUM2 EXTENDED EDITION）引擎笔记

调查对象：`WHITE ALBUM2\WA2.exe`（1,220,608 字节，PE32，链接时间 2011-12-27，无加壳）
和 `WHITE ALBUM2 Special Contents\WA2_Special.exe`（942,080 字节）。两者文字机制相同，下面地址以 WA2.exe 为准，
Special 的地址在括号里。

## 文字显示：只用位图字库

- exe 没有导入 CreateFont / TextOut / GetGlyphOutline 等 GDI 文字函数，画面上的字全部来自 `fnt.pak` 的 TGA 字库。
- `fnt.pak`（KCAP）有 4 张字库，在 0x4188af 起载入到贴图槽 0x1c4–0x1c7：

  | 贴图槽 | 文件 | 尺寸 | 格子 |
  |---|---|---|---|
  | 0x1c4 | 本体80.tga | 3200×3840 | 40 px |
  | 0x1c5 | 袋影80.tga（描边） | 3200×3840 | 40 px |
  | 0x1c6 | 14pt本体.tga | 1920×2304 | 24 px |
  | 0x1c7 | 14pt袋.tga（描边） | 1920×2304 | 24 px |

  TGA 是 type 1（256 色调色板，调色板 32 位 BGRA，左下角起点）。本体和描边分开两张。
  fnt.pak 里另有 `old`、`vssver2.scc` 等开发残留目录项，不用理会。
- 每张都是 80 列 × 96 行 = 7680 格，实际用了 7655 格。

- 调色板索引的意思（`tools/pcglyph.py`）：
  本体80 0–31 = 描边区灰阶（alpha 0）、32–63 = 字身 alpha；袋影80 0–63 = 描边 alpha；
  14pt本体 0–31 = 字身 alpha；14pt袋 0–42 = 描边 alpha。
- 原字位置：40px 格里汉字墨迹约 26px、中心 (19, 18.5)，描边外扩约 2px；24px 格里约 11px、中心 (10.5, 10)，外扩 1px。
  俊羽圓體 Medium 28px / 10px 和原字大小对得上（原字更细）。

## 字码 → 格子序号

- `0x401050`（Special 0x401053 附近）：查区段清单 `0x4a14b8`（Special 0x49e4b8），
  u16 (lo, hi) 成对，0xFFFF 结束，共 59 段。序号 = 前面各段 (hi−lo+1) 之和 + (code−lo)。
  **段长包含 trail byte 0x7F 那一格**（所以一整行是 189 格）。查找是线性的，段的先后次序无关，可以在末尾追加新段。
  - 单字节：0x20–0x7D（94 格）、0xFFB1–0xFFDD（半角ｱ–ﾝ，符号扩展后的值，45 格）→ 0–138
  - 双字节：0x8140 起，按 cp932 的有字区段，直到 0xEAA4；然后 0xF040–0xF0C0（129 格）；最后 IBM 扩展 0xFA40–0xFC4B。
  - 另一张 0x4a1420（36 段，只到第一水准汉字，3728 格）只在参数为 0 时使用；唯一调用者 0x4463e4 传 1，所以用不到。
- 唯一调用者 `0x4463e4`（在 0x4462e0 的绘字函数里）：
  列 = 序号 % 80、行 = 序号 / 80（常数写死 80，`imul 0x66666667; sar 5`），
  格子大小 40.0（0x4a22d8）或 24.0（0x4a2b78，esi ≥ 2 时用 14pt 字库）。坐标以像素传，贴图加高应该不用改 UV 常数（待实测）。
- 双字节在调用前做了 `rol ax, 8`（脚本里是 SJIS 字节序）。

## 0xF040–0xF0C0：现成的空位

- 贴图里这 129 格只有 0xF07F 一格有图（一个点），其余全空；两个版本所有脚本（main 379 项、Special 461 项）都没有用到 0xF0xx。
- 前导字节判定：
  - `0x433ff0`：lead ≥ 0x81 且不在 0xA0–0xDF，trail ≥ 0x40 → 0xE0–0xFF 都接受。
  - `0x444114`、`0x44db80`：0x81–0x9F、0xE0–0xEA、**0xF0**。
  所以 0xF0xx 和 0x85xx/0x86xx（JIS 空行，但在 0x81–0x9F 内）都能通过所有判定，不用改判定代码。
  0xEB–0xEF、0xF1 以上则要改这两处（可能还有别处，未查全）。
- `0x443b20` 一带（`font%02d.fd%d`、区段表 0x4c22c0，已有 0xF040–0xF047）是引擎旧的 .fd 字库路径，WA2 没有 .fd 文件，应该用不到。

## 新字需要量

- 粤语字幕（ic_ass 全部 .ass）里 cp932 编不出的字：445 个（嘅佢你呢噉啲嚟㗎冇…），出现 50,262 次。上限估计，实际按入游戏的句子算。
- 0xF040–0xF0FC（188，跳过 0x7F）+ 0x8540–0x86FC（2×188）= 564 个位置，够用。

## 封包

- `script.pak`、`fnt.pak` 都是 KCAP（`tools/pc_kcap.py` 已能解；压缩项是 LZSS，未压缩项 flag=0）。
- exe 里有 `%s\%s`、`char\buf\%s` 等路径格式，是否会优先读散文件（例如 `fnt\本体80.tga`）未确认。

## 两个 exe

- 两个 script.pak 都有 1001–1013、5000–5104；Special 另有 4000–4030、5200–5401、6xxx、7xxx（PS3 追加内容）。
- 外传 5000–5004 在哪个 exe 的菜单里玩，待实测。

## 实测（2026-10-17，tools/test2.py）

- 区段表搬到 .text 尾部、追加 F0C1–F0FC / 8540–85FC / 8640–86FC，字库加高到 102 行：游戏正常启动，
  F040 段、F0C1、0x8540 起的新字在对白和回放记录里都正确显示。贴图加高不用改 UV 常数。
- 压缩流全用字面量（不压缩）的 LZSS，游戏照读。
- 回放记录用的也是 40px 字库；25 个全角字一行在回放记录里放得下。
- 错误：Python 的 cp932 把 擎、增 等 IBM 扩展字编成 NEC 选定区 0xEDxx/0xEExx，引擎没有这区 → 空白。
  编码时要改成 0xFAxx–0xFCxx。
- 新字（俊羽圓體 Medium）比原字库粗很多，混排很显眼 → 计划把用到的汉字全部重画。

## 半角字的前进量

- 绘字函数 0x446500（Special 0x447f..，ebp 栈帧）。单字节字：笔位 += 字号/2 + 字距/2（主程序 0x4471e8–0x447209，
  字串 [esp+0x20]、下标 ebp、字号 [esp+0x28]、字距 [esp+0x164]、笔位 [esp+0x24]；Special 0x448d20–0x448d43，
  字串 [ebp-0xd4]、下标 [ebp-0xc8]、字号 [ebp-0xe4]、字距 [ebp+0x1c]、笔位 [ebp-0xd0]）。全角：笔位 += 字号 + 字距。
- 字体描述的参考字号是 28（格子 40），所以字宽表以 28 为基准，全角 = 28，原版半角 = 14。
- 0x445b90 一带也有同样的半角前进代码，但属于旧 .fd 字库路径（调用 0x443b20），用不到。
- 早先「区段表搬到 .text 尾部空隙」的做法已改为放进新节 .yue。
